## 1. Which migrations are pending?

**Short answer: the repo cannot prove it — and that is itself the #1 finding.** Migrations are applied by hand in the Supabase SQL editor, so there is no `schema_migrations` history to read, and my sandbox cannot reach your Supabase host to probe.

**What I built for you:** `scripts/check-pending-migrations.mjs` (new, committed to your project). It probes a signature object (table / column / view / function / seeded row / bucket) for ~95 of the 116 migrations, read-only, and prints APPLIED / PENDING lists plus SQL-editor queries for the ~20 that can't be probed via REST (constraint-only, trigger-only, publication-only files). Run:

```bash
node scripts/check-pending-migrations.mjs
```

**Most-likely-pending shortlist (from repo evidence), in order of probability:**

1. `supabase/migrations/20260716120000_social_calendar.sql` — the newest file; its verify script and rollback were authored in the same session, the classic "written, awaiting your SQL-editor run" pattern.
2. `20260716090000_offer_campaign_cancelled_status.sql` — `OFFER_FLYER_HANDOFF.md` says twice "the human must apply this." **Until applied, cancelling an offer campaign hard-fails on the DB CHECK constraint** — this is a live bug if pending.
3. `20260716100000_offer_prepare_permission.sql` — same handoff; after applying, remember to grant `offer.prepare` to non-admin flyer designations in Settings → Access & Roles.
4. `20260716110000_offer_campaign_lifecycle.sql` — same handoff (adds `completed_at`/`archived_at`; the auto-archive cron needs it).
5. `20260715090000_clients_module_permissions.sql` — "app works either way" migration, the kind that silently never gets run.
6. The 20260714 finance batch (8 files, 090000–180000) — probably applied July 14–15 (verify scripts exist) but the repo holds no confirmation; treat as apply-unverified.
7. `migrations/005_granular_permissions.sql` + `006_rls_enforce_auth.sql` — flagged "status unverified" in two handoff docs since weeks ago. **Highest blast radius of anything in this list**: 006 replaces the permissive `allow_all` RLS policies with permission-gated ones. If 006 is *not* applied, your RLS is still allow-all (see §3, S-6).

### Migration-system problems found (deep analysis)

- **Two migration directories** (`migrations/` numbered 001–025 and `supabase/migrations/` timestamped) that are **interleaved in time and cross-dependent**: root `014` FK-references `ad_projects` (created in supabase `20260628120000`); root `019` needs `task_requests` (supabase `20260610120000`); root `024` publishes `invoice_expense_items` (created by a loose file). A naive "replay one directory then the other" rebuild fails. No single file records the true global order.
- **17 loose non-timestamped files** in `supabase/migrations/` (`phase1…phase11`, `cashbook_invoice_link*.sql`, `invoice_sequence.sql`, etc.) that the Supabase CLI would **silently ignore**, and whose alphabetical order is wrong as a run order (`phase10` sorts before `phase2`).
- **Duplicate numbering:** two `003_` files; no `004_` exists. The `20240001–20240004` files carry fake 2024 prefixes though authored in July 2026, sorting before everything.
- **Type conflict / broken function overload (HIGH):** `20260629090000` adds `system_jobs.locked_by TEXT` + `dequeue_jobs(TEXT,…)`; `20260629120000` adds `locked_by UUID` via `ADD COLUMN IF NOT EXISTS` (no-ops if 090000 ran first, leaving TEXT) and defines `dequeue_jobs(UUID,…)` — a **second overload**, not a replacement. Result: PostgREST `rpc/dequeue_jobs` can be ambiguous, and the UUID version assigning into a TEXT column errors at runtime. Fix: drop the TEXT overload, align the column type explicitly. (Check: `select data_type from information_schema.columns where table_name='system_jobs' and column_name='locked_by'`.)
- **Idempotency is patchy.** `fix_migrations.py` only rewrote files ≥ 20260629090000 and missed `CREATE UNIQUE INDEX`, `CREATE MATERIALIZED VIEW`, `RENAME COLUMN`, and `CREATE POLICY` — so the AI-foundation migrations (124000/125000/130000), `20260523070451`, `phase10`, and `supabase-schema.sql` all error if re-run.
- **CHECK-constraint churn is order-sensitive.** `task_requests_status_check` was rewritten 3 times, `ad_reports_template_check` 3 times, `offer_campaigns_status_check` 2 times. Applying these out of order silently regresses the allowed status set.
- **Rollbacks cover only 9 of 116 files**, and even inside the covered window, `20260714120000` and all three `20260716` offer migrations have none.
- **Destructive/no-undo migrations** worth knowing about: `007` (deletes contribution rows — applied, per handoff), `20260523082156/082852` (renumber already-issued payslips), `20260703140000` (soft-deletes legacy ad-fund allocations; a second run after new allocations exist would migrate those too), `20260705150000` (drops a column).

**Recommendation (migrations):** adopt one convention going forward — everything timestamped in `supabase/migrations/`, applied with `supabase db push` (or at minimum: after each manual SQL-editor apply, run `INSERT INTO supabase_migrations.schema_migrations(version) VALUES ('<timestamp>')` so history exists). Fold the root `migrations/` dir and loose files into an ordered `docs/migration-history.md` + freeze them. Add a squashed baseline (`supabase db dump`) so a fresh environment doesn't need the un-replayable 116-file chain.

## 2. Bugs and errors (new findings, verified where marked)

Severity-ordered. ✅ = I personally re-verified the code after the audit pass.

### Critical

- **B1 ✅ Unauthenticated service-role job-queue mutation.** `src/app/(dashboard)/dashboard/admin/jobs/actions.ts` — `retryJob`, `cancelJob`, `fetchJobsSummary`, `fetchRecentJobs` are `'use server'` exports using `createAdminClient()` with **zero auth check**. Server actions are POST-addressable endpoints regardless of which page renders them: any visitor who obtains the action ID can reset/cancel any background job or enumerate the queue. Fix: `requirePermission`/admin check at the top of each.

### High

- **B2 ✅ OAuth callbacks accept unsigned `state` and no session** — `src/app/api/auth/google/callback/route.ts` (also `auth/meta`, `advertising/oauth/meta`). `state` is plain base64 JSON (`{clientId, employeeId}`), never verified against a nonce, and no Supabase session is required before upserting provider tokens via service role. An attacker can bind their own ad-account tokens to any victim client and forge `connected_by`. Fix: signed state + nonce cookie + session check.
- **B3 ✅ Invoice totals silently drop `previous_balance`.** `invoices-client.tsx` — `updateDiscount` (~line 970) and `removeDiscountLog` (~line 989) compute `total = sub + tax − discount` **without** `+ previous_balance`, while the sibling `applyDiscount`/`updatePreviousBalance` include it. Editing a discount on an invoice carrying a previous balance silently erases that receivable from the total. The same omission exists in `removeItem` (~723), `updateTaxRate` (~740), and expense-delete (~3462).
- **B4 Payment recording is a client-side read-modify-write** (`handlePayment`, ~1048): `newPaid = inv.paid_amount + applied` from local state, written as an absolute value. Two near-simultaneous payments → the second overwrites the first; both payment rows exist but `paid_amount` reflects one. Should be an atomic server-side increment (RPC).
- **B5 Payment "Undo" leaves phantom cash** (~1110): the undo toast deletes the payment row and restores `paid_amount`, but never removes the cashbook inflow + allocation that `recordInvoicePayment` created. Undo a ₹10,000 payment → ₹10,000 phantom inflow stays in the Cash Book.
- **B6 Invoice issue-date shifts to the previous month (IST)** — `getInvoiceDateForTaskMonth` (~1533) and the batch path (~1753) build a local-midnight Date then `.toISOString().split('T')[0]`: in Asia/Calcutta, Sep-1 00:00 IST → `issue_date = '2025-08-31'`. Invoice number says `INV-2509` while the stored date is August — due-date/overdue math runs a month early. Use local date formatting, never `toISOString()` for calendar dates.
- **B7 Contributions save = delete-then-reinsert with no error checks** — `contributions-client.tsx` `handleSave` (~1071): deletes `contributions`/`task_tools`/`contribution_scores` then re-inserts; the success toast and local-draft deletion run unconditionally. If the insert fails after the delete succeeded, earnings rows are permanently wiped while the user is told "saved". Needs a transactional RPC + error branches.
- **B8 ✅ Cashbook edit silently discards Income/Expense type change** — `cashbook-client.tsx` (~483–515): the edit form exposes the type toggle and local state applies `form.type`, but the payload sent to `updateCashbookEntry` **omits `type`** (and the server action never persists it). The UI flips, totals recompute — and on reload it reverts.

### Medium

- **B9 Non-atomic number generation** — invoice numbers (`lib/invoices/numbering.ts`), task numbers, CQIDs (settings): SELECT-max-then-insert; concurrent creation produces duplicates. Move into DB sequences/RPCs (the receipt-number RPC is the in-house pattern to copy).
- **B10 Quotation→invoice number parsing** (`quotations-client.tsx` ~163) derives "next sequence" from the last dash-segment of `INV-YYMM-…`, which is the *client code*, not a sequence → unpredictable jumps and collisions.
- **B11 Month-overflow date math** — recurring cashbook entries use `setMonth(m+1)` (~546): a Jan-31 monthly entry → Mar 3 (Feb skipped, March doubled). Similar `new Date(yr, mo, 0).toISOString()` UTC-shift drops last-day-of-month expenses from the batch-rebilling sweep (invoices-client ~1702).
- **B12 `deletePayment` matches the cashbook entry by date+type only** (~1158) — two same-day payments and deleting the small one can remove the large one's cashbook entry/allocation.
- **B13 Cross-currency sums** — invoice statements/CSV exports (~1950, ~2203, ~2331) add `total_amount` across AED+INR invoices under one symbol instead of using the `*_inr` snapshots the rest of the app uses.
- **B14 Middleware fails open** (`lib/supabase/middleware.ts` ~222): a transient employee-lookup error skips route gating for that request. Also the 60s signed-cookie permission cache delays revocation, and its HMAC silently disables if the service key env is absent.
- **B15 Swallowed write errors** — a recurring pattern: `saveAssignments` (tasks-client ~1450, delete-then-insert, empty `catch {}`), quotation items insert (~343), cashbook insert/edit/delete have no failure branch, and many settings/tasks inline edits patch local state without checking the result. Failed writes look saved until reload. This is the single most bug-prone *pattern* in the codebase.
- **B16 `updateRecommendationStatus`** (`advertising/actions/ai-actions.ts` ~67) mutates AI insights with no permission guard; `upsertDailyMetricInternal` (`advertising/actions.ts` ~687) is an exported unguarded service-role writer of ad spend (its own comment says it bypasses checks) — move it out of the `'use server'` module.

### Low (selected)

- `/api/logo` redirects to any stored URL — mild open-redirect if settings are compromised.
- `campaigns/actions.ts` `acknowledgeLogs`/`resyncSheet` gate on signed-in only, no campaign permission.
- Dead Cmd/Ctrl+S in the task edit modal (`editFormRef` never attached).
- Advertising report routes check permission but not per-project ownership (horizontal read).

### Verified clean

All 11 `vercel.json` cron routes check `CRON_SECRET` fail-closed; no committed secrets in `src/` (the leaked GitHub PAT from `INVESTIGATION_2026-07-15.md` §5 is a separate, still-open item — revoke it); no dangling imports of the four deleted offer-intake components; token flows validate expiry/ownership. I could not run `tsc`/`next build` here (npm registry 403 in sandbox) — the `.ts-errors.log` at the root is from July 9 and predates dependency install, so treat it as stale. Run `npx tsc --noEmit` locally for the definitive type answer.

### RLS exposure (database-side, related to bugs above)

**S-6:** 16 migrations create tables with **RLS never enabled** — including `payslip_emails` (salary data), `provider_connections` (ad-platform tokens), `employee_commission_agreements`, and the entire public-portal surface (`task_requests`, `intake_links`, `agencies`, `request_activity`, `request_revisions`). Another ~10 tables have RLS enabled but `USING (true)` policies misleadingly named "admin". Because the app mostly mutates via service role this hasn't bitten yet, but any anon/auth-key path (and the client-side mutation pattern the handoffs already flag) can read these. Worth a dedicated RLS pass once you confirm whether `006_rls_enforce_auth` is actually applied.

## 3. Duplicate setups and repeated features

Verified status of suspected duplicates — some good news first: **AI capture is NOT duplicated** (all three entry points — `/api/shortcut`, Requests, `/dashboard/capture` — share one parse layer), **offer-prepare fully reuses the offer-intake client** (zero copy-paste), and the old `buildInvoiceHtml` duplication documented in the review docs is **already fixed** (the docs are stale, not the code).

Real duplication found, ranked by consolidation value:

1. **Two `createAdminClient` implementations** — `lib/supabase/admin.ts` (validates env, no session persistence) vs `lib/supabase/server.ts` (neither). 71 files import one, 58 the other, picked seemingly at random. Keep `admin.ts`, re-export from `server.ts`. Trivial fix, high value.
2. **Two permission/user-resolution stacks** — `lib/permissions/check.ts` (cached, used by 63 pages) vs `lib/auth/enforce.ts` (uncached, re-implements the identical lookup, used by 31 actions). Every guarded action pays duplicate DB round-trips and the logic can drift. Make `enforce.ts` call `loadCurrentUser()` internally.
3. **Currency list defined 6+ times** (types, quick-create modal, fx sync, 3 import schemas, 2 symbol maps + receipt modal). Adding a currency requires ~8 edits today. One `CURRENCIES` const + derived type.
4. **Three parallel LLM provider stacks** — hardened `lib/ai/groq.ts`, the advertising AI registry's own un-hardened `GroqProvider` (re-introducing the exact failure mode groq.ts documents avoiding), and `lib/reporting/ai-engine.ts` calling OpenAI by raw fetch, bypassing the registry that already has an OpenAI adapter. ~1,400 lines total; fold to one registry.
5. **PDF/rasterization** — `lib/partners/statement-image.ts`/`statement-pdf.ts` self-admittedly mirror `lib/invoices/download-pdf.ts` (and duplicate a 20-line `loadHiddenIframe` between themselves). Extract a shared `lib/raster.ts`.
6. **CSV export hand-rolled 7×** (three copies inside invoices-client alone), with inconsistent BOM/quote-escaping — plus **two hand-rolled CSV parsers** in the two import wizards (the catalog one breaks on quoted commas) while the installed `csv-parse` dependency is used by nothing but `_archive/`.
7. **Four notification paths** — the real system (`lib/notifications/create.ts` + web push), a **half-built native-push channel** (`native_push_tokens` accumulate; no sender exists — build or remove), the Requests Resend-email path with its own HTML shell, and a byte-identical WhatsApp URL builder in 2 exports + 2 inline copies.
8. **Formatting** — `formatCurrency` has 8 importers while raw `toLocaleString('en-IN')` appears 211× in 74 files; `date-fns` is installed for exactly 4 advertising files while 52 files hand-roll dates. Pick one convention.
9. **The advertising module is a parallel world** (~11,450 lines): own KpiCard, EmptyState, formatCurrency, AI registry, date library. Needs a conventions pass more than a merge.
10. **Dependency duplicates**: `@base-ui/react` used in exactly 1 file (button) alongside 11 `@radix-ui` packages; `satori` direct-dep duplicated by `next/og`'s bundled copy; `pg` + `csv-parse` effectively unused; `shadcn` (a CLI) in runtime deps.

**Dead weight safe to remove:** root `test-db.js`, `test_db.ts`, `test_db2.ts`, `test_fetch.ts`, `test_query.ts`, `apply-migration.js`, `fix_migrations.py`, `supabase-schema.sql` (superseded), `.ts-errors.log`, 7 empty `src/components/*` directories, the publicly-routable dead mockup at `/portal/mockup`, ~12 one-off `scripts/check-*`/`debug-*` files, and `_archive/` (752 KB). The 14 root handoff/design `.md` docs (3,571 lines) contain stale claims (e.g. the invoice-HTML duplication) — consolidate into `docs/` with a one-line status header each.

## 4. Improvements & ease-of-use (prioritized)

`CIRQLE_SYSTEM_REVIEW.md` already ranks 20 product improvements (its top 5 remain right: cron for recurring tasks + payroll drafts, consolidate Insights, window the big fetches, Smart-Focus dashboard, AI capture in dashboard). What follows is what *this* audit adds — engineering/ease-of-use, not repeated from that doc:

**Do this week (small, high leverage):**
1. Add auth guards to `admin/jobs/actions.ts` (B1) and `upsertDailyMetricInternal` (B16). Minutes of work, closes the worst holes.
2. Run `node scripts/check-pending-migrations.mjs`, apply what's pending (the three `20260716` offer migrations first — one of them un-breaks campaign cancel), and record applied versions somewhere durable.
3. Fix the `previous_balance` omissions (B3) and the cashbook `type` omission (B8) — both are one-line-diff class bugs with real money impact.
4. Unify `createAdminClient` and the currency constant (duplications #1, #3).
5. Delete the dead-weight list above; revoke the leaked GitHub PAT if not already done.

**Do this month (structural):**
6. **Kill the client-side-mutation pattern.** B3–B8, B12, B15 are all the same disease: money math and multi-table writes in browser components using the anon client, optimistic state, and unchecked results. The handoffs already list the four files to convert to server actions — this audit found six more money bugs living in exactly that pattern. One shared `mutate()` helper that surfaces errors + a rule "no `.from().update()` in client components" prevents the whole class.
7. **Atomic money operations as RPCs**: payment increment (B4), invoice/task/CQID numbering (B9, copy the receipt-number RPC pattern), contribution save (B7 as a transaction).
8. **One date/currency utility** (`lib/format.ts`): `formatDate`, `formatCurrency`, `localDateStr` (the `toISOString` timezone bugs B6/B11 all die here). Mechanical, wide, worth it.
9. **Migration hygiene** as in §1: single directory, timestamps only, history recorded, squashed baseline, rollback per destructive migration.
10. **RLS pass** on the 16 un-RLS'd tables, starting with `payslip_emails` and `provider_connections`.

**Ease-of-use / DX quality of life:**
11. `npm run check` = `tsc --noEmit && eslint && vitest run` — the handoffs' "definition of done" as one command.
12. A `docs/` index: one README pointing at the live docs, archiving stale handoffs — new contributors currently meet 14 root-level .md files, several of which contradict the code.
13. `requirePagePermission()` helper to replace the identical 4-line stanza in ~50 pages, and a shared `getClientOptions()` for the 13 verbatim `clients` select copies (also centralizes archived-filtering, which currently varies).
14. Surface background failures to users: sheet-sync errors on the Requests row, and replace silent `catch {}` with a toast + retry pattern (one `reportError()` helper).
