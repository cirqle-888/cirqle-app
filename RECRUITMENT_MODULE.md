# Recruitment / Careers Module

Full hiring pipeline: a public application form on cirqle.work → this CRM's
Recruitment module (Open Positions / Applications / Interviews / Offers /
Reports) → hire. No email-based applications anywhere — every submission is
a row in `job_applications`, written server-side.

## Architecture decisions worth knowing

**No `application_activity` table.** The original spec asked for four
supporting tables including `application_activity`. This codebase already has
a universal, permission-aware activity timeline (`activity_logs` +
`src/lib/activity/{log,timeline,timeline-copy}.ts`, Cirqle Connect Wave A) used
by every other module. Per this project's own rule ("reuse existing helpers,
do not duplicate"), recruitment events are logged there instead, via a new
`activity_logs.application_id` scope column (mirrors `client_id` / `project_id`
/ `task_id` from migration 014). `<TimelineTab scope={{ applicationId }} />` on
the applicant profile page is the same component every other module uses.

**Two tables beyond the requested four.** `application_interviews` and
`application_offers` were added because "Interview Management" and the
"Offers" page both need real backing state — a `stage` string on
`job_applications` alone can't hold a schedule, an interviewer, a meeting
link, or an offered salary/expiry date.

**Public route uses the admin client, like `/intake` and `/start`.** The
`/careers/apply` page and its actions run entirely server-side against the
Supabase admin (service-role) client — the same pattern as every other
public-token page in this app. RLS on all six new tables still exists as
defense-in-depth (`REVOKE INSERT/UPDATE/DELETE FROM authenticated, anon`), so
there is no direct browser write path even if someone tried.

**Internal notes are structurally private.** Applicants never get a Supabase
auth account, so there is no RLS policy that could ever grant them access to
`application_notes` (or anything else in the module) — "applicants cannot see
internal notes" is true by construction, not just by convention.

## Database

Tables (migration 020): `job_positions`, `job_applications`,
`application_notes`, `application_documents`, `application_interviews`,
`application_offers`, plus the support table `hr_reference_sequences` and one
new column on the existing `activity_logs` (`application_id`).

Reference numbers: `CIRQLE-HR-{YYYY}-{seq:04d}` (e.g. `CIRQLE-HR-2026-0001`),
generated by the `generate_hr_reference_number()` Postgres function — same
atomic counter-table pattern as migration 011's cashbook receipt numbers, so
concurrent submissions can never collide.

Pipeline stages (`job_applications.stage`, drag-and-drop in the kanban):
`new → screening → interview_scheduled → interview_completed →
technical_review → selected → offer_sent → joined`, with `rejected` reachable
from any stage. The DB does not enforce ordering — a card can be dragged to
any column — matching real hiring workflows where candidates get rejected or
fast-tracked at any point.

Storage: private bucket `recruitment-resumes` (15MB limit), same 2-step
signed-upload-URL pattern as `chat-attachments` (migration 016) — the
applicant's browser uploads directly to Supabase Storage; the server never
touches file bytes.

**Run `migrations/020_recruitment.sql` in the Supabase SQL editor before
anything else works.** Nothing auto-applies it.

## Permissions

Seeded by the migration: `recruitment.view`, `recruitment.edit`,
`recruitment.delete`, `recruitment.interview`, `recruitment.admin`. Grant
these to designations in **Settings → Designations** (new "Recruitment"
module section). Admins always have every permission automatically.

`recruitment.interview` exists for a narrower "interviewer only" role but
isn't yet enforced as a separate gate anywhere in the code — today,
`recruitment.edit` (or admin) covers scheduling and recording outcomes. Add a
dedicated check if you want interviewers who can't otherwise edit the
pipeline.

## Notifications

New `NotificationType`s: `application_received` (→ all admins),
`interview_scheduled` (→ the assigned interviewer), `interview_reminder` (→
interviewer, or all admins if none assigned — sent once per interview by the
daily cron, 24-48h ahead), `candidate_selected` (→ all admins, on stage move
to Selected), `offer_accepted` (→ all admins).

## Website integration (cirqle-portfolio-final-main)

`src/pages/Careers.tsx`'s `APPLY_URL` now defaults to
`https://app.cirqle.work/careers/apply` (was a `mailto:` fallback — removed
entirely, no email path remains). Override with `VITE_CAREERS_APPLY_URL` in
`.env` if the route ever moves. No form lives in the Vite site itself; the
"Apply" buttons just link out to the CRM-hosted form, same as the original
code comment intended ("tokenized intake link") — it's just not tokenized
since this is a genuinely public form, not a per-client link.

## Hardening before high traffic (not yet built)

- **CAPTCHA**: only a honeypot field + a 10-minute duplicate guard exist
  today. Add Cloudflare Turnstile or hCaptcha to `apply-client.tsx` /
  `careers/apply/actions.ts` before this URL gets meaningfully advertised.
- **Rate limiting** by IP on `submitApplication`/`getResumeUploadUrl` (there's
  a `submitted_ip` column reserved on `job_applications` for this, currently
  unused).
- **Resume malware scanning** — files land straight in Supabase Storage with
  no scanning step.
- **`recruitment.interview` as its own gate** (see Permissions above).

## Testing checklist

1. Run migration 020 in Supabase SQL editor.
2. Settings → Designations → grant `recruitment.*` to the relevant roles.
3. Create an Open Position.
4. Visit `/careers/apply` (logged out / incognito) and submit an application
   with a resume — confirm the reference number screen appears and no email
   was sent anywhere.
5. Confirm an admin notification appeared and the application shows up in
   the Applications kanban at stage "New".
6. Drag the card through a few stages; open the applicant profile and check
   Resume Preview, add an Internal Note, schedule an Interview, create and
   send an Offer, mark it Accepted — confirm the Activity Timeline tab shows
   every one of these events.
7. Confirm Reports numbers move accordingly.
8. `npx tsc --noEmit`, `npx eslint`, `npm test` all green.
